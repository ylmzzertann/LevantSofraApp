# Levant Sofra

The design handoff (`design_handoff_levant_sofra`) implemented as a real app.

One product, two audiences, one codebase:

- **In-restaurant guests** scan the QR sticker on their table, land on `/t/12`, and order from their seat.
- **Online customers** open the site, build a bag, enter an address, pay.

Same menu data, same item detail, same bag — two shells and two checkout tails.

```bash
npm install
npm run dev
```

Then open <http://localhost:3000> for the web site, and <http://localhost:3000/t/12> for the table flow (resize below 768px, or use device emulation, to see the phone shell).

## Stack

Next.js 15 (App Router) · React 19 · TypeScript · CSS Modules. No UI library and no CSS framework — the design specifies exact pixel values and one motion curve, and a token layer in plain CSS reproduces that more honestly than utility classes would.

There is no backend yet. All state lives in a React reducer and is mirrored to `localStorage`; card fields are deliberately excluded from what gets stored.

## How the two shells work

The Phone/Desktop switch in the prototype was a demo device and is gone. The real rule is the viewport:

| Route | ≥ 768px | < 768px |
|---|---|---|
| `/` | W1–W4 — the web site: header, hero, menu, sticky order panel, footer | M2 — the phone menu screen |
| `/bag` `/address` `/pay` `/done` `/item/[id]` `/saved` `/orders` | the same screens in a centred 620px cream sheet on the backdrop | full-viewport phone screens |
| `/t/[table]` | (a QR is a phone thing, but it renders in the sheet) | M1 — QR landing |

The switch is pure CSS (`.ls-mobile-only` / `.ls-desktop-only` in `globals.css`), so there is no viewport guessing on the server and no layout flash on the client.

Every screen route uses the same three-band shell — fixed header, scrolling body, fixed footer — from `components/shell/AppShell.tsx`. On the phone the stage is exactly `100dvh` and only the body band scrolls; that is what keeps the bag bar and the primary action reachable as content grows.

```
    site/SitePage.tsx     W1–W4
  data/menu.ts            the menu — shaped like GET /menu will be
  lib/                    money, bag lines, totals — pure, reusable server-side
  state/store.tsx         reducer, actions, persistence
```

`lib/totals.ts` and `lib/bag.ts` have no React in them on purpose: the backend has to recompute both, and it should import the same functions rather than reimplement the arithmetic.

## The bag line

The one model detail worth knowing. A bag entry is keyed by **dish + exclusions + note**, never by dish id:

```
key = id + (excl.length ? '|' + excl.sorted().join(',') : '') + (note ? '|' + note : '')
```

So "Muhammara" and "Muhammara, no walnut" are two separate rows, while the menu row shows their combined count. Quantity changes and removals address the key.

## Money

```
subtotal = Σ price × qty
discount = promoOn ? subtotal × 0.10 : 0
delivery = online ? (subtotal >= 60 ? 0 : 4.90) : 0
service  = online ? 0 : subtotal × 0.05
tipAmt   = (subtotal − discount) × tipRate        // never on service or delivery
preTip   = subtotal − discount + delivery + service   // the bag screen's Total
total    = preTip + tipAmt                            // the payment screen
due      = split > 1 ? total / split : total
```

The bag total is tip-free so the rows shown there sum exactly to the total beneath them. Format: `$` + two decimals with a trailing `.00` stripped (`$11`, `$24.15`).

The only live promo code is `LEVANT10`.

## Deliberate departures from the prototype

- **Ingredients are a real field.** The prototype derived them by splitting the description on commas. `data/menu.ts` models them as `{ id, label, removable }`, and non-removable ones (the lamb in a kebab) render dashed and untappable rather than with a tap affordance the kitchen can't honour. The handoff flagged this as production work.
- **Segmented pills are 44px tall**, against the prototype's ~37px. The handoff sets 44px as the tap-target floor and these are primary controls; the two rules collide and the accessibility floor wins. Small circular controls (the 29px `+`, the steppers, the category chips) keep their drawn size and grow their hit area with a transparent pseudo-element instead.
- **The grain is a PNG tile**, `public/grain.png`, generated by `npm run grain` — the handoff asks for exactly this rather than re-rasterising an SVG `feTurbulence` per element. It only sits on non-scrolling layers.
- **Sold-out rows** got a minimal treatment (muted row, disabled `+`, a "Sold out" chip) because `available` is in the backend contract. The handoff lists this as not designed; treat it as a placeholder.
- **Fonts are self-hosted** at build time via `next/font/google`, so nothing is requested from Google at runtime.
- The bag starts empty. The prototype seeded three plates to demo the screens.

## Photography

Every photo is a labelled placeholder (`components/media/PhotoSlot.tsx`). Pass it a `src` and the same component renders an optimised `next/image`. Slots: the site hero, the item-detail hero, the address map crop, and the menu-row thumbnails (currently the tinted plate glyph). Still needed: one shot of the room, one square-croppable shot per dish, in the same warm daylight the palette implies.

## Next: the backend

The client is written so each of these is a swap, not a rewrite.

| Endpoint | Replaces | Notes |
|---|---|---|
| `GET /menu` | `data/menu.ts` → `getMenu()` | categories `[{ key, label, sub, items: [{ id, name, price, desc, long, tag, ingredients[], available }] }]` |
| `POST /sessions/qr` | the `table` path segment in `app/t/[table]/page.tsx` | returns `{ tableId, tableLabel }`; the path segment is currently trusted, which a real deployment must not do |
| `POST /orders` | `placeOrder` in `state/store.tsx` | `{ mode, tableId?, lines:[{ dishId, qty, exclusions[], note }], address?, when, promoCode?, tip, split, paymentMethod }` → `{ orderNo, totals }`. **Exclusions and notes must travel per line to the kitchen ticket** — that is the whole point of the feature, and the KITCHEN COPY block on M7 is meant to mirror what the pass actually prints. |
| `POST /promos/validate` | `validatePromo` in `lib/totals.ts` | `{ valid, percentOff, message }` |
| payment intent | the stub in `PayScreen.submit` | card / Apple Pay / Google Pay. Card details currently never leave the browser and are never persisted; keep it that way — go through a provider SDK so the PAN never touches our server. |
| `GET /orders/history` | `SEED_ORDERS` in `state/store.tsx` | |
| `GET \| PUT /favourites` | `state.favs` | |

Totals must be recomputed server-side at order time — `lib/totals.ts` is written to be imported by both sides so the two can't drift.
